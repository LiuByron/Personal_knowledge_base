## 一、先建立全局：项目里有哪些「智能」

项目里其实有 **三种不同形态的「智能」**，各自的设计逻辑不同。先分清，后面才不会混：

| 形态 | 位置 | 设计 | 一句话 |
| --- | --- | --- | --- |
| **对话智能体** | `agent/` + `assistant/` | LangGraph `createReactAgent`（ReAct 循环），挂 6 个工具 | 「会用工具的聊天助手」，自主决定调哪个工具 |
| **工作流智能体** | `dispatch/` + `agents/` | LangGraph `StateGraph` 有向图 + `interrupt` 人工闸门 | 「跑项目的流水线」，节点固定但中间要人确认 |
| **员工流程** | `employee/` | 手动状态机（Map + 表落库） | 「走审批的数字员工」，线性流程逐步确认 |

三者都调 LLM，但**编排方式完全不同**：

- 对话智能体：**LLM 自己决定下一步**（ReAct，发散、不可预测）
- 工作流：**图结构固定**，LLM 只负责单个节点（评估、决算），流程由代码控制（收敛、可预期）
- 员工流程：**线性状态机**，最确定，几乎不用图

> **核心认知**：不是所有业务都要「全交给 AI」。**越需要确定性（审批、账务），越要用代码控制流程、让 LLM 只做单点任务；越需要开放性（对话、理解意图），越要把控制权交给 LLM。**

这就是本项目的智能体设计哲学。

## 二、框架选型：为什么选 LangChain + LangGraph

### 2.1 市面上有哪些选择

| 方案 | 优点 | 缺点 | 适合 |
| --- | --- | --- | --- |
| 裸调 OpenAI/DeepSeek SDK | 零依赖、完全可控 | 没有 Agent/工具循环/流式封装，全手写 | 简单问答 |
| **LangChain** | 生态全：模型封装、消息、工具、链 | 抽象层厚，版本变动大 | 通用 LLM 应用 |
| **LangGraph** | 图编排、`interrupt` 闸门、`checkpointer` 断点、流式 | 学习曲线陡、async 上下文有坑 | 有状态/多步/需人工确认的 Agent |
| OpenAI Agents SDK / Swarm | 轻量、多 agent 编排 | 绑定 OpenAI；DeepSeek 兼容性需验证 | 轻量多 agent |
| AutoGen / CrewAI | 多 agent 对话、角色扮演 | 重、抽象多、难控 | 多 agent 协作研究 |
| 自研框架 | 完全掌控 | 成本极高，重造轮子 | 有特殊需求的大团队 |

### 2.2 为什么是 LangChain + LangGraph 组合

本项目的选型逻辑，一条条拆：

1. **DeepSeek 走 OpenAI 兼容协议** → LangChain 的 `ChatOpenAI` 只需配 `configuration.baseURL` 指向 DeepSeek 端点，**消息格式、流式、工具调用全部复用**。零成本接入国产模型（成本、合规、可用性都可控）。
2. **需要「Agent + 工具」** → LangChain 的 `tool()` + zod schema 让定义工具非常简单，模型自动生成 tool_call。
3. **需要「有状态、可打断、可恢复」** → 这正是 LangGraph 的强项：
   - `createReactAgent` 开箱即用的 ReAct 循环（思考→调工具→再思考）
   - `interrupt()` + `Command(resume)`：**人工闸门**（审批、选方案）
   - `checkpointer`（PostgresSaver）：状态落数据库，**重启/断线可续跑**
   - `recursionLimit`：硬截断防死循环
4. **生态与团队**：文档全、案例多、技术栈（NestJS + TypeScript）契合，团队成员/AI 协作工具熟悉。

### 2.3 这个选择的好处

- **开发效率高**：Agent 循环、工具调用、状态持久化都是框架能力，不手写
- **能力可叠加**：加一个业务能力 = 加一个工具（zod schema），不改路由代码
- **人工闸门是框架原生**：`interrupt` 把「AI 流程里插入人类审批」做成了语言级能力
- **可观测**：`streamMode`、callback 钩子、checkpoint 都能看运行轨迹

### 2.4 这个选择的代价（新手要心里有数）

- **抽象层厚 = 黑盒**：Agent 内部发生了什么要扒源码；一旦框架行为异常（如 interrupt 逃逸），定位困难
- **框架 API 变动快**：LangGraph 从 0.x 到 1.x 改过不少接口，升级要跟
- **async 上下文陷阱**：本项目就栽过——agent 工具里调 `interrupt()` 会读到错误 config，导致中断逃逸（见第四章）
- **类型复杂**：`Annotation`、`RunnableConfig`、checkpointer 泛型，TS 报错时需要耐心
- **thinking 模型的兼容限制**：DeepSeek 的 thinking 模型不支持强制 `tool_choice` / `withStructuredOutput`（见第七章）

### 2.5 什么时候该考虑换

- 只做「一句话问答」→ 裸 SDK 就够了，别上 LangGraph
- 需要多 agent 大量并行/角色扮演 → 看看 OpenAI Agents SDK / 自研
- 框架升级频繁且你们被坑 → 用轻量自研（但**别轻易自研**，成本很高）

**结论：本项目业务（对话 + 有状态工作流 + 人工审批）与 LangGraph 的能力模型高度匹配，选型是成立的；代价主要是学习成本和框架黑盒。**

## 三、核心架构决策：为什么这样设计

### 3.1 单 Agent（挂 6 工具）vs 多 Agent

**本项目**：对话主链路是**一个** ReAct Agent，挂 6 个工具。

**为什么不做多 Agent 路由**（比如「规划 Agent」「文档 Agent」各一个）？

- 业务上，用户和 AI 的对话是连续的，意图经常混合（「先规划，再说明文档」）
- 单 Agent + 多工具，**LLM 在同一上下文里自主选择工具**，天然支持混合意图
- 多 Agent 要处理通信、上下文传递、死锁检测（见 `gcj.md` §8），复杂度陡增

**好处**：简单、上下文单一、工具自主路由（加能力=加工具）。
**弊端**：
- 单一上下文窗口，长对话 + 多工具结果可能挤压
- LLM 可能「选错工具」（幻觉），依赖描述质量
- 工具多了容易互相干扰（建议 ≤10 个，本项目 6 个）
- 无法并行执行多个独立任务

**何时升级多 Agent**：意图明显分域、各域需要独立记忆/工具集、需要并行。本项目暂不需要。

### 3.2 工具式路由 vs 代码路由

两种「决定调哪个工具」的方式：
- **代码路由**：`if (msg.includes('规划')) planRoute()` —— 可控但呆板，新意图要改代码
- **工具式路由**（本项目）：LLM 看工具 `description` 自主决定 —— 灵活，新能力=加工具

**好处**：加「四职能助手」时零路由改动，就是加 4 个工具。
**弊端**：LLM 可能误调。**平衡手段**：
- 每个工具的 `description` 写详细（模型靠它决策）
- zod schema 严格（参数类型、必填）
- 工具内部二次校验（防「幻觉参数」，见 `gcj.md` §3.2）
- 危险工具加人工闸门（如采购必须 `start_employee_workflow` 走审批）

### 3.3 Agent 全局单例 + AsyncLocalStorage

**设计**：`agentProvider` 组装一次 ReAct 图，全局单例，所有用户/会话复用。请求级 `userId` 不进单例，用 `userContext.run(userId, () => agent.invoke(...))` 包裹，工具内 `currentUserId()` 读取。

**为什么**：
- agent 组装昂贵（模型实例、工具绑定），每个请求重建不可接受
- 单例**不能持有请求态**，否则多用户互相污染

**好处**：性能、无状态可并发。
**弊端**：工具读 userId 要经过 AsyncLocalStorage 的间接层，心智负担 + 忘包 `userContext.run` 就会读不到。

**关键点**：这条链必须完整——`assistant.service` 里 `userContext.run` 包住 `agent.invoke`，工具函数里 `currentUserId()`。**改这块时务必保持这个模式。**

### 3.4 确定性任务用独立模型（温度 0）

**设计**：`SUMMARIZE_MODEL`（温度 0）与 `CHAT_MODEL`（温度 0.7）分开。

**为什么**：对话要「发散、自然」（高温度）；摘要、评估、结构化提取要「稳定、可复现」（温度 0）。同一个输入，温度 0 几乎每次结果一致，适合落库的确定性数据。

**好处**：评估结果可预期、决算可复核、摘要稳定。
**弊端**：多一个模型实例，配置多一层。
**平衡**：确定性任务**优先走 SUMMARIZE_MODEL**，别用对话模型凑合。

## 四、人工闸门：手动状态机 vs LangGraph interrupt

这是本项目最有价值的权衡，值得单独一章。

### 4.1 两种方案在项目里的应用

| 场景 | 方案 | 代码位置 |
| --- | --- | --- |
| 项目工作流（评估→规划→选路→决算） | LangGraph `interrupt()` + `Command(resume)` + PostgresSaver | `dispatch/project.graph.ts`、`dispatch.service.ts` |
| 员工采购流程（立项→比价→采购确认→文档） | 手动状态机（Map 缓存 + `EmployeeFlow` 表） | `employee/employee.service.ts` |

### 4.2 为什么项目工作流用 interrupt

`project.graph.ts` 在 `evaluate`、`select`、`settle` 三个节点里调 `interrupt(...)`：

```ts
const requirement = await deps.evaluate(state.description)
const resume = interrupt({ type: 'confirm_requirement', requirement })  // 暂停，等人确认
if (!resume?.approved) return { stage: 'cancelled' }
```

`interrupt` 的机制：抛出内部 `GraphInterrupt` → LangGraph 捕获 → **把断点快照写入 checkpointer** → 图暂停 → 外部用 `Command({ resume })` 恢复 → 从断点继续。

**好处**：
- **状态天然持久化**：断点落 PostgreSQL，进程重启也能恢复
- **图结构清晰**：闸门就是图里的一个点，流程可视
- **框架原生**：不用自写状态机

**前提**：dispatch 走**独立端点**（`POST /dispatch/project`），调用链完全可控。

### 4.3 为什么员工流程用手动状态机（而不是 interrupt）

`employee.service.ts` 顶部注释说得很清楚（这是踩坑换来的经验）：

> **不用 LangGraph interrupt/checkpointer**——员工图经 agent 工具启动时运行在 agent 的 async 上下文中，`interrupt()` 读到的是 agent 的 runnable config，GraphInterrupt 逃逸且 checkpoint 不落盘，`Command(resume)` 无法恢复。

**通俗解释**：
- `start_employee_workflow` 是 agent 的一个**工具**，在 `agent.invoke` 的 async 上下文里执行
- 此时调 `interrupt()`，LangGraph 找不到「正确的图 run 上下文」，中断异常逃逸到 agent 外层，断点没存进数据库
- 结果：流程「看起来暂停了」，但**无法恢复**——审批按钮点了没反应

**手动状态机的做法**：
```ts
// 内存 Map 缓存当前进程内的流程；每个状态流转都同步落 EmployeeFlow 表
private readonly threads = new Map<string, EmployeeThread>()
// stage 流转：confirm_proposal → compare → confirm_procurement → finalize
```

**好处**：线性流程简单直接、完全可控、不依赖框架的 async 上下文。
**弊端**：
- Map 只是缓存，重启后靠 DB 重灌（`findFirst({ threadId, userId })`）
- 并发/跨实例需自己保证（当前单实例够用）
- 状态机代码自维护（新状态要自己加分支）

### 4.4 怎么选：interrupt 还是手动状态机（决策准则）

| 判断维度 | 用 LangGraph interrupt | 用手动状态机 |
| --- | --- | --- |
| 调用方式 | **独立端点**调用图 | 经 agent 工具启动 |
| 流程形态 | 多分支、可重规划（图结构） | 线性、分支少 |
| 需要断点恢复 | 是（长流程、跨重启） | 是（但要自己落库） |
| 团队对框架掌控力 | 强 | 一般 |
| 复杂度 | 图 + checkpoint 开销 | 简单直接 |

**核心经验（本项目的血泪）**：**经 agent 工具启动的流程，不要依赖 LangGraph interrupt**——async 上下文会让它不可靠。独立端点的流程，interrupt 是优雅的选择。

## 五、上下文与记忆的四层设计

### 5.1 为什么不能「只截断最后 N 条」

很多项目简单 `messages.slice(-10)`（见 `gcj.md` §1.1）。问题：
- 丢关键上下文：用户 5 轮前说的约束，AI 忘了
- 开发者**无感知**：回答变差但不知道原因
- 越早的信息越容易被截掉，但早期往往是需求本源

### 5.2 本项目的四层设计

`assistant.service.ts` 的 `stream()` 组装输入：

| 层 | 来源 | 作用 | 预算控制 |
| --- | --- | --- | --- |
| 核心层（SystemPrompt） | 能力声明 + 会话滚动摘要 + 安全规则 | 设定人设/规则/背景 | — |
| 检索层（注入参考资料） | 长期记忆（top5）+ 偏好 + 知识库片段 | 跨会话记忆 + 文档依据 | KB 1800 token（`fitToBudget`） |
| 工作层（历史） | 最近 40 条消息 | 本轮对话上下文 | 总预算 50K 内裁历史 |
| 本轮输入 | 用户消息 + 上传文件文本 | 当次请求 | 单条 ≤10000 字符、文件 ≤20K 字符 |

**关键机制**：
1. **历史取「最近」而非「最旧」**：`orderBy desc take 40` 再反转（初版取最旧 40 条是 bug，见提交记录）
2. **总 token 预算裁剪**：`fitHistoryToTokens` 从最旧开始裁，直到总输入 ≤50K（64K 窗口留输出余量）
3. **滚动摘要**：消息数达 20 条，把旧消息压缩进 `Conversation.summary`，删除原消息行（增量摘要，LLM 失败则跳过——降级）
4. **长期记忆异步抽取**：每次对话后 fire-and-forget 抽偏好/事实/决策/教训，向量化存库

### 5.3 好处与弊端

**好处**：关键信息多层兜底（摘要兜历史、记忆兜跨会话、RAG 兜文档），token 有预算不溢出。
**弊端**：
- 层数多，组装逻辑复杂，每层都有预算/阈值参数要调
- 摘要是有损压缩，细节可能丢（用「记忆抽取」补偿）
- 记忆/知识库检索可能注入噪音（用相似度阈值 0.4 过滤）

### 5.4 平衡

- 追求「不丢上下文」→ 多留历史、记忆、摘要
- 追求「成本/延迟」→ 收紧预算、提高阈值
- 本项目取 40 条 + 50K 预算 + 0.4 阈值的组合，是「够用且不失控」的平衡点

## 六、流式策略：非流式 invoke + 模拟打字机

### 6.1 现状

`assistant.service.ts` 用 `agent.invoke()`（**非流式**）跑完整个 ReAct 循环，拿到完整回答后**切成小块（24 字符）间隔 18ms 推送**，模拟打字机效果。思考过程（reasoning）同样分块流式。

### 6.2 为什么不用真流式（`agent.stream`）

| 对比 | 真流式（stream） | 本项目（invoke + 分块） |
| --- | --- | --- |
| 首字延迟 | 低（边生成边推） | 高（等整个 ReAct 跑完，含工具调用） |
| 实现复杂度 | 高（要处理 token 流 + 工具事件流混合） | 低（一次性结果，简单可靠） |
| 工具中间过程 | 可实时看到 | 事后统一透传（reasoning 事件） |
| 与现有事件模型契合 | 需改造 | 契合（token/route_plan/data_result 事件） |
| 稳定性 | 流中断/竞态多 | 高 |

**本项目选择 invoke 的原因**：
- 业务上，**规划场景必须等工具结果**（路线算完才能回答），流式首字优势不明显
- 事件模型（`route_plan`/`data_result`/`employee_gate`）需要完整工具结果，非流式后处理更清晰
- 非流式简单、稳定、易测试

### 6.3 好处与弊端

**好处**：简单可靠、事件透传清晰、abort 语义简单（signal 传给 invoke 即可）。
**弊端**：工具链长的请求，用户要等较久才看到首字（有「正在思考」动画 + reasoning 分块缓解）；不是真流式，长回答体验打折扣。

### 6.4 未来升级路径

若想真流式：`agent.stream()` + LangGraph callback（`handleLLMNewToken` / `handleToolStart`），把 token 和工具事件实时推 SSE。代价是处理流混合、竞态、abort。**当前非流式够用，等用户体验成为瓶颈再升级。**

## 七、结构化输出：兼容 DeepSeek thinking 的取舍

### 7.1 为什么不能直接 `withStructuredOutput`

`evaluation.service.ts` / `procurement.service.ts` / `memory-extract.service.ts` 的注释揭示了关键坑：

> DeepSeek 的 thinking 模型强制 `tool_choice`（function calling）会报 "Thinking mode does not support this tool_choice"；`json_object` response_format 又要求 prompt 含 'json' 字样且不被严格校验 schema。

**通俗说**：DeepSeek 思考型模型对「强制结构化输出」的支持有限制，LangChain 的 `withStructuredOutput` 底层走 tool_choice，会直接报错。

### 7.2 本项目的做法：手动 prompt + 三层防护

1. **Prompt 里明确要求**：「只输出一个 JSON 对象（不要 markdown 代码块、不要多余文字）」+ 字段说明
2. **解析容错**（`common/structured.ts`）：
   - `extractJSONBlock`：优先提取 ```json 代码块，其次首个 `{...}`
   - `JSON.parse`
   - zod schema 校验（字段 `catch` 兜底：null/缺失 → 默认值）
   - **任一环节失败 → 返回 fallback，不 throw**
3. **业务校验单独做**：如「缺起终点」在 `evaluate()` 里单独判断抛错，与「格式错误」区分开

### 7.3 好处与弊端

**好处**：兼容 thinking 模型；解析失败不拖垮上层（evaluation 会提示、memory-extract 静默）；schema 校验保证字段类型。
**弊端**：
- 依赖正则提取，极端输出（嵌套 `{}`、JSON 里有 JSON 字符串）可能误判
- fallback 会丢失信息（失败就空结构）
- 手动 schema 与业务类型要人工保持同步

### 7.4 平衡

- 要「严格」→ zod `strict` 模式 + 校验失败重 prompt（成本高）
- 要「健壮」→ `catch` 兜底 + fallback（本项目）
- 本项目取健壮优先：**AI 输出格式不稳是常态，宁可降级也别崩**

## 八、可靠性设计要点

把散落各处的关键点集中列一遍（每项都能在代码里找到）：

| 要点 | 实现 | 为什么 |
| --- | --- | --- |
| **recursion_limit** | agent 25；dispatch 图 25 | 硬截断 ReAct 循环，防工具死循环 |
| **LLM 超时** | 120s | 防挂死 |
| **重试** | maxRetries 2 | 网络瞬时错误自动重试 |
| **maxTokens** | 4096（env 可调） | 限制输出长度、防成本失控 |
| **abort** | `res.on('close') → abort()` | 客户端断开中止 LLM，防资源泄漏 |
| **SSE 心跳** | 15s `: heartbeat` | 防代理空闲断连 |
| **SSE 连接上限** | 每用户 3 / 全局 1000 | 防连接数耗尽 |
| **Token 预算** | 输入 50K、KB 1800、文件 20K 字符 | 防上下文溢出 |
| **降级链** | 摘要失败跳过、备用模型（可选）、错误固定文案 | LLM 不可用不崩 |
| **越权防护** | 会话/线程/项目按 userId 归属校验 | 防 IDOR |
| **结构化校验** | 三层防护 | 输出格式不稳不崩 |

**设计哲学**：每一个「AI 不可靠」的点，都要有一个**代码层面的兜底**——超时、预算、校验、降级、abort。AI 是不可控的，工程要可控。

## 九、权衡的艺术：如何平衡

这是智能体开发的终极问题。把本项目遇到的所有平衡点列成一张表：

| 维度 | 往左偏（简单/稳） | 往右偏（强/复杂） | 本项目取舍 |
| --- | --- | --- | --- |
| 编排方式 | 代码控制（员工状态机） | 全交给 LLM（ReAct） | 对话用 ReAct，流程用代码，审批用手动 |
| 框架 vs 手写 | 手写（可控） | 框架（高效） | 用框架，但知道它的坑（interrupt） |
| 流式 | invoke（简单） | stream（体验） | invoke + 模拟打字机 |
| 结构化输出 | 健壮 fallback | 严格校验 | 健壮优先，兼容 thinking |
| 上下文 | 少而精（省 token） | 多而全（不丢） | 四层 + 预算控制 |
| 人工介入 | 全自动 | 每步确认 | 关键闸门人工（立项/选路/决算） |
| 工具数量 | 少（6 个） | 多（能力广） | 6 个，够用且不混乱 |
| 温度 | 0（确定） | 高（发散） | 对话 0.7、确定性 0 |

**几条通用准则（从本项目提炼）**：

1. **确定性需求用代码，开放性需求用 LLM**——审批、计算、落库用代码；理解、组织、生成用 LLM。
2. **LLM 能干的交给 LLM，但每个不可靠点都要有兜底**——超时、预算、校验、降级、abort。
3. **复杂流程先用最简单的方案**——员工流程最初就想用 interrupt，失败后才退到手动状态机。别一开始就上重型方案。
4. **人工闸门放在真正需要的地方**——立项、选方案、决算确认是业务关键，必须人确认；普通聊天不该每句都要确认。
5. **成本与质量的平衡靠预算参数调**——token 预算、相似度阈值、maxTokens 都是旋钮，别写死。
6. **宁可降级也别崩**——AI 输出格式错、LLM 挂了，返回友好提示/跳过，不能中断用户流程。

## 十、智能体开发检查清单

新增/修改一个智能体能力时，对照检查：

- [ ] **模型封装**：走 Symbol token Provider，不用裸 `new ChatOpenAI`；超时/重试/maxTokens/temperature 都设了
- [ ] **工具**：zod schema 完整、description 详细、内部二次校验 + try/catch 返回错误文本（不抛）
- [ ] **循环控制**：`recursionLimit` 已设
- [ ] **上下文**：历史取最近、token 预算裁剪、该层记忆/RAG 注入正确
- [ ] **结构化输出**：三层防护 + fallback，不 throw
- [ ] **人工闸门**：危险操作有确认；经 agent 工具启动的流程不用 interrupt
- [ ] **userId 传播**：经 `userContext.run` 包裹，工具内 `currentUserId()`
- [ ] **越权**：查会话/线程/项目带 userId 归属
- [ ] **abort/心跳**：SSE 端点有 abort + 心跳 + 连接守卫
- [ ] **降级**：LLM 失败有兜底（跳过/固定文案/备用模型）
- [ ] **测试**：新增逻辑配单测（容错、越权、状态流转）
- [ ] **安全**：System Prompt 加固、注入内容隔离、错误不泄露
